# RN and Expo integration verification

Verified on 2026-09-10. This record supports the [production architecture](architecture.md), specifically the React Native host and Expo integration. Existing OtaKit transport, billing, event authentication, and accepted shared-system tradeoffs are not reopened by this review.

**Result: 25 checks passed; 7 published npm tarball integrities and 32 source-file hashes verified.** This establishes the inspected upstream behavior and the JavaScript adapter prototypes below. Native implementation and device acceptance remain work to complete under architecture section 13.

The September 11 [delivery review resolution](review-resolution.md) adds separate executable design cases for payload/baseline identity, platform/runtime versioning, manifest cleanup, path validation and retry behavior. The 25 upstream probes below do not verify those new contracts or their eventual native/backend implementation. Capacitor's existing v2 workflow remains the compatibility requirement.

## Reproduce

From the repository with its existing dependencies available, Node 22 or later, `tar`, and network access:

```sh
node research/react-native-ota/verify-integration.mjs
```

The [probe script](verify-integration.mjs) reads [integration-sources.json](integration-sources.json), downloads exact npm artifacts, checks their SHA-512 integrity, and reads selected tar members without installing those packages or running lifecycle scripts. It verifies selected file SHA-256 hashes and downloads/checks the pinned RN sources. It transpiles and executes the actual published Expo DOM and Constants modules with explicit native-module stubs. Native checks inspect source contracts; they do not execute Swift, Objective-C, Kotlin, or Java.

The successful run used Node 24.16.0 and the repository's TypeScript 5.9.3. No reference dependencies were installed. The verifier writes no package or product files and exits nonzero on an integrity, source-contract, or behavioral mismatch.

## Executed probes

The 25 checks comprise 13 dependency/source checks, 8 executions of upstream JavaScript behavior, and 4 checks of the proposed adapter mechanics. The adapter checks use the actual Constants object produced by the published source, but the wrappers and launch contexts are small research prototypes in the script.

- Embedded DOM/config behavior for iOS and Android; enabled Expo Updates behavior as a control.
- Native development and web DOM behavior remain unchanged.
- Disabled Updates with a retained manifest still affects Constants.
- A new Constants facade can change `expoConfig` without altering the original non-configurable property, native build value, manifest getter, or named exports.
- A DOM URI containing spaces remains correctly encoded when the component filename is appended.
- An old instance's frozen config/DOM context does not change when a newer selection is prepared.
- Rollback selects the earlier config and DOM root together; embedded fallback delegates to Expo.

## Remaining implementation evidence

The first implementation work package is the production package's local-artifact release fixture. It must prove host reload, early instance binding, and composed Metro resolution before the backend migration depends on them. The adapters use internal Expo module identities, so every supported SDK upgrade requires resolution and bundling checks.

Native acceptance must exercise foreground/background races, headless service starts and normal exits, task listeners during reload, Activity/scene recreation, protected iOS storage, process death around durable state writes, and old-instance readiness. Provider-specific background scheduling outside RN callbacks needs its own fixture. The conservative deferral policy is specified; no native race-freedom claim is made by the source probes.

Expo acceptance must export and load new DOM components, CSS, images, and fonts offline on both platforms; preserve Router, custom Metro resolution, splash, native actions, and Reanimated; and verify config/DOM rollback using both `@expo/dom-webview` and its documented `react-native-webview` alternative. Actual Metro interception, Hermes compilation, source maps, and WebView loading were not run in this review.

The [complete acceptance matrix](architecture.md#13-implementation-order-and-production-acceptance) also covers current OtaKit ZIP/delta/encryption formats, v2 Capacitor compatibility, v3 target isolation, readiness, analytics, packaging, and migration. A native package is supportable only after those checks pass for its published version matrix.
